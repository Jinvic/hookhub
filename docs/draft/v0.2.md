# HookHub 设计文档（草案 v0.2）

> **一句话定位**：HookHub 是一个可插件化扩展的 Webhook 中间件——从任意服务接收 Webhook，按规则解析、转换并转发到任意目标。
>
> *Receive webhooks from anywhere, route them anywhere.*

相对 [v0.1](v0.1.md)：对齐仓库命名、明确 at-most-once、推迟 CEL，并按「先骨架与一例适配、再连接」重组实现顺序。

---

## 0. 决策记录（相对 v0.1）


| 决策          | 取值                                                                                       |
| ----------- | ---------------------------------------------------------------------------------------- |
| 投递语义        | **at-most-once**：先 ACK，内存队列尽力投递；进程崩溃 / 重试耗尽 / 队列满可丢，文档明示                                 |
| 命名          | 跟仓库：`model.Event` / `model.Message`、`source.Source`、`target.Target`（不用 Sink / `event` 包） |
| 路径语义        | `/hook/{name}` = `sources` 配置**实例名**；`driver` 选插件实现                                      |
| 命名消歧        | 配置用 `driver`（插件）；`Event.Type` / `match.type` 表示**事件种类**（如 `task.reminder.fired`）          |
| 条件表达式       | **v0.2 不做 CEL**；路由先靠 `source` + 事件 `type` 精确 / 通配匹配                                     |
| 实现顺序        | 骨架 → 一例 Source + 一例 Target 验证模型 → 再接 Router / 配置 / 队列                                    |
| 包结构         | 扁平：不拆 `router` / `pipeline` / `queue` 等多包；编排放 `internal/app`                             |
| 配置依赖        | `gopkg.in/yaml.v3` + `os.ExpandEnv`；不上 Viper / koanf                                     |
| HTTP Target | 默认只允许配置声明的 URL / 前缀，禁止任意用户可控 URL（防 SSRF）                                                 |
| 去重时机        | **成功入队后**标记 `Event.ID`；失败耗尽不再依赖上游自动重投恢复                                                  |

## 1. 背景与目标



### 1.1 问题

各类 SaaS / 自建服务（Vikunja、GitHub、Gitea、Uptime Kuma…）都支持 Webhook 推送，但：

- 推送内容是**原始 JSON**，直接接入 IM / 通知服务（ntfy、Slack、邮件）可读性差；
- 每个服务的 payload 结构不同，逐个硬编码对接成本高、难维护；
- 一个事件往往要**扇出**到多个目标（手机推送 + 群通知 + 存档）。



### 1.2 目标

- **多来源接入**：统一入口 `/hook/{name}` 接收不同服务的 Webhook。
- **统一事件模型**：各来源解析为统一的 `model.Event`，下游与来源解耦。
- **配置化路由**：用 YAML 定义「匹配规则 → 模板渲染 → 投递目标」，常见需求零代码。
- **可插件扩展**：新增来源 / 目标 = 新增一个文件 + 注册，不改核心流程。
- **尽力投递**：异步处理、失败重试、幂等去重、可观测（不保证不丢）。



### 1.3 非目标（v0.2 不做）

- 可视化 Web UI / 规则编辑器。
- 多租户 / 权限体系。
- 分布式部署与集群调度（单实例起步）。
- CEL / `when` 条件表达式。
- 持久化队列、死信队列、跨进程恢复。

## 2. 总体架构

```
                  ┌─────────────────┐
 Vikunja ─POST──▶ │ /hook/vikunja   │─┐
 GitHub  ─POST──▶ │ /hook/github    │─┤   ┌────────┐   ┌──────────┐   ┌────────┐
 Gitea   ─POST──▶ │ /hook/gitea     │─┼──▶│ Router │──▶│  Render  │──▶│ Target │──▶ ntfy / Slack / ...
 ...     ─POST──▶ │ /hook/{name}    │─┘   │(rules) │   │(template)│   │ (send) │
                  └─────────────────┘     └────────┘   └──────────┘   └────────┘
                        │                      ▲
                   Source 插件            配置驱动 (config.yaml)
                 (验签 + 解析 → Event)
```

**数据流**：

1. HTTP 入口按 `{name}` 找到配置实例，再按 `driver` 找到 Source 插件；
2. Source 验签并解析为统一 `Event`；
3. Router 用配置规则匹配 Event，产出若干 Action；
4. 对每个 Action 渲染模板，生成 `Message`；
5. Target 将 `Message` 投递到目标，失败按策略重试，最终可丢。

**设计原则**：

- **三层解耦**：Source（来源）→ Event（统一模型）→ Target（目标），核心流程对具体服务无感知。
- **配置优先**：能用 YAML 表达的绝不写代码；模板不够用时再降级到脚本（后续）。
- **编译期插件**：注册表 + 显式注册（`init` 或 main 中 blank import），单二进制分发。
- **先验证模型再连接**：P1 用硬编码路径打磨 `Event` / `Message`，P2 再上配置路由。

## 3. 核心数据模型

包路径：`internal/model`。P1 期间允许按真实 Vikunja / ntfy payload **微调字段**；改动后同步本文档。

### 3.1 Event（统一事件）

```go
type Event struct {
    ID      string         // 幂等键：source + type + payload hash
    Source  string         // 配置实例名，如 "vikunja"
    Type    string         // "task.reminder.fired"
    Time    time.Time      // 事件发生时间（优先取 payload，否则接收时间）
    Subject string         // 可选摘要，如 task.title
    Data    map[string]any // 解析后的结构化数据
    Raw     []byte         // 原始 body，供模板兜底与调试
    Headers http.Header
}
```



### 3.2 Message（待投递消息）

```go
type Message struct {
    Title    string
    Body     string
    Format   string            // "text" | "markdown"
    Priority string            // 可选紧急度提示；Target 映射或忽略
    Extra    map[string]string // Target 扩展，如 ntfy tags/click
}
```



### 3.3 Action / Route（配置模型，P2 引入）

```go
type Route struct {
    Name    string
    Match   Match
    Actions []Action
}

type Match struct {
    Source string // 精确匹配配置实例名，如 "vikunja"
    Type   string // 分段通配，如 "task.reminder.*"
}

type Action struct {
    Target   string
    Config   map[string]any
    Template Template
}

type Template struct {
    Title    string
    Body     string
    Format   string
    Priority string
    Extra    map[string]string // 如 ntfy tags: "bell,warning"
}
```

**通配规则（定死）**：

- `Type` 按 `.` 分段；每段为精确字符串或单个 `*`。
- `*` 只匹配恰好一段（不含 `.`）。
- 例：`task.reminder.*` 匹配 `task.reminder.fired`，不匹配 `task.reminder`；`task.*` 不匹配 `task.reminder.fired`。
- 空 `Type` 表示匹配该 Source 下全部类型。

## 4. 插件接口



### 4.1 Source（`internal/source`）

```go
type Source interface {
    Name() string // 插件 driver，如 "vikunja"
    Verify(req *http.Request, body []byte, cfg map[string]any) error
    Parse(req *http.Request, body []byte) (*model.Event, error)
}
```

- `Verify`：验签 / 共享密钥校验；可用通用策略（`none` 需显式配置、`hmac`）。
- `Parse`：将原始请求转为 `Event`；`Event.Source` 由调用方填入**配置实例名**（非插件 driver，若二者相同则可复用）。



### 4.2 Target（`internal/target`）

```go
type Target interface {
    Name() string // 插件 driver，如 "ntfy"
    Send(ctx context.Context, msg *model.Message, cfg map[string]any) error
}
```



### 4.3 注册表

```go
type Registry struct {
    sources map[string]Source
    targets map[string]Target
}

func (r *Registry) RegisterSource(s Source) { /* by s.Name() = driver */ }
func (r *Registry) RegisterTarget(t Target) { /* by t.Name() = driver */ }
```

- 提供可注入的 `Registry`，便于测试；进程内可保留默认全局实例。
- 插件可在 `init()` 自注册，**main 须 blank import 拉入插件包**，避免链接器剔除。
- 新增一种服务支持 = 新增一个文件 + 注册，主流程零改动。

## 5. 配置设计



### 5.1 示例（Vikunja → ntfy）

```yaml
server:
  addr: ":8080"
  log_level: info

sources:
  vikunja:                    # 实例名 → /hook/vikunja
    driver: vikunja           # 插件实现
    secret: "${VIKUNJA_WEBHOOK_SECRET}"

targets:
  ntfy-work:                  # 实例名，供 routes 引用
    driver: ntfy
    base_url: https://ntfy.sh
    token: "${NTFY_TOKEN}"

routes:
  - name: vikunja-reminder-to-ntfy
    match:
      source: vikunja         # 匹配 Event.Source（实例名）
      type: "task.reminder.*" # 匹配 Event.Type（事件种类）
    actions:
      - target: ntfy-work
        config:
          topic: work-tasks
        template:
          title: "{{ .Data.task.title }}"
          body: |
            项目：{{ .Data.project.title }}
            提醒时间：{{ .Data.reminder.reminder }}
            链接：https://vikunja.example.com/projects/{{ .Data.project.id }}
          format: markdown
          priority: high
          extra:
            tags: "bell"
```

同一 `driver` 可配置多个实例（不同密钥 / 不同 Vikunja），路径与 `match.source` 均使用**实例名**。

### 5.2 配置要点

- **环境变量插值**：`${VAR}` 在加载时用 `os.ExpandEnv` 替换，避免密钥落盘。
- **模板引擎**：Go `text/template`，上下文为 `Event`（`{{ .Data.xxx }}`、`{{ .Subject }}`、`{{ .Type }}`）。
- **缺字段**：渲染失败则该 Action 记错误并跳过，**不阻断**同 Event 的其他 Action。
- **通配匹配**：见 §3.3；无 CEL / `when`。
- **扇出**：一个 Route 的多个 Action、多个 Route 匹配同一 Event，均会执行；彼此错误隔离。

## 6. 处理流水线

```
HTTP Handler
  ├─ 1. 按 path {name} 查 sources 配置实例 → driver → Source 插件
  ├─ 2. 读取 body（上限默认 1MB）
  ├─ 3. Verify（失败 401）
  ├─ 4. Parse → Event；填入 Event.Source = 实例名（失败 400）
  ├─ 5. 若 ?debug=1：只记日志，返回 200，不入队
  ├─ 6. 尝试入队；成功则标记 Event.ID 已见，立即返回 200
  │     └─ 队列满：丢弃，打错误日志，仍返回 200（at-most-once）
  │     └─ ID 已在 LRU：返回 200，跳过入队
  └─ 7. 异步处理
        ├─ Router.Match(event) → []Action
        ├─ 对每个 Action：渲染模板 → Message
        └─ Target.Send（超时 + 重试 + 日志）；单 Action 失败不影响其他
```

**语义（写死）**：


| 项     | 行为                                                     |
| ----- | ------------------------------------------------------ |
| 投递保证  | **at-most-once**：ACK 后尽力投递，不保证送达                       |
| 先 ACK | 避免上游超时重投风暴                                             |
| 去重    | 内存 LRU（默认 1 万条）；**成功入队后**写入                            |
| 重试    | 指数退避（如 1s / 5s / 30s / 2m，最多 4 次）；超时 / 5xx 可重试，4xx 不重试 |
| 最终失败  | 记失败日志并丢弃；不做死信                                          |
| 进程崩溃  | 内存队列中未处理事件丢失                                           |
| 背压    | 有界队列；满则丢弃并打日志                                          |


P0 / P1 可同步调用 Target（无队列）；P3 再引入异步与去重。同步阶段同样按 at-most-once 理解（handler 已 200 后失败不回滚上游）。

## 7. 目录结构

扁平布局，对齐现有仓库；编排暂不拆成多包。

```
hookhub/
├── cmd/hookhub/main.go       # 入口：加载配置、注册插件、启动 HTTP
├── internal/
│   ├── model/                # Event、Message、Route（已有）
│   ├── source/               # Source 接口、Registry、vikunja、generic（后续）
│   ├── target/               # Target 接口、Registry、ntfy、http（后续）
│   └── app/                  # HTTP handler、路由匹配、模板渲染、队列/重试（按需增长）
├── config.yaml.example
├── Dockerfile
├── Makefile
└── README.md
```

模块职责：


| 模块       | 职责                           |
| -------- | ---------------------------- |
| `model`  | `Event` / `Message` / 配置侧结构体 |
| `source` | 验签 + 解析；按 driver 注册          |
| `target` | 投递；按 driver 注册               |
| `app`    | 配置加载、HTTP、匹配、渲染、队列与重试        |

## 8. 可靠性与可观测性



### 8.1 可靠性

- **验签**：每个 Source 实现 `Verify`；`none` 需显式配置。
- **幂等**：`Event.ID` + LRU；见 §6。
- **超时**：Target 调用默认 10s `context` 超时。
- **重试 / 背压 / 可丢**：见 §6。



### 8.2 可观测性

- **结构化日志**（`log/slog` JSON）：`event_id` / `source` / `type` / `route` / `target` / `duration` / `result`。
- **调试模式**：`/hook/{name}?debug=1` 只记录原始 payload，不转发。
- **健康检查**：`/healthz`、`/readyz`。
- **指标**：Prometheus `/metrics` 放到 P4，可选。

---



## 9. 安全设计

- Webhook 验签（HMAC / Token），密钥经环境变量注入。
- Body 大小限制（默认 1MB）。
- 模板使用 `text/template`，不执行任意代码。
- **通用** `http` **Target**：只允许配置中声明的 `url` / `base_url`（或前缀白名单）；**默认开启**，禁止把请求中的 URL 直接当作转发目标。
- 日志脱敏：`token`、`secret` 等字段不落明文。

## 10. 技术选型


| 项    | 选型                                | 理由             |
| ---- | --------------------------------- | -------------- |
| 语言   | Go                                | 单二进制、并发好、与仓库一致 |
| 配置   | `yaml.v3` + `os.ExpandEnv`        | 够用、依赖少         |
| 模板   | `text/template`                   | 标准库、安全         |
| 条件   | 通配匹配（无 CEL）                       | 降低依赖与调试成本      |
| 日志   | `log/slog`                        | 标准库、结构化        |
| 去重   | `hashicorp/golang-lru`（或手写有界 map） | 简单高效           |
| HTTP | `net/http`（Go 1.22+ `ServeMux`）   | 无需框架           |

## 11. 里程碑

每个阶段结束后系统可独立使用；P1 即可自用。


| 阶段          | 内容                                                                      | 预估      |
| ----------- | ----------------------------------------------------------------------- | ------- |
| **P0 骨架**   | `/hook/{name}`、Registry、`/healthz`、可编译运行（空 Source/Target 或 stub）        | 0.5–1 天 |
| **P1 一例适配** | Vikunja Source + ntfy Target；硬编码一条转发；用真实 payload 打磨 `Event` / `Message` | 1–2 天   |
| **P2 连接**   | YAML 配置、`source` + 事件 `type` 通配路由、`text/template`、扇出、env 插值            | 1–2 天   |
| **P3 可靠**   | 有界内存队列、重试、LRU 去重、结构化日志、debug 模式                                         | 1–2 天   |
| **P4 按需**   | generic source、http target、更多插件、CEL、Prometheus                          | 按需      |


**推荐节奏**：P0 → P1 用真实 Vikunja 事件验证模型 → 按需改 `model` → 再进入 P2。

## 13. 附录：Vikunja Source 解析示例

```go
func (v *VikunjaSource) Parse(_ *http.Request, body []byte) (*model.Event, error) {
    var p struct {
        EventName string         `json:"event_name"`
        Time      time.Time      `json:"time"`
        Data      map[string]any `json:"data"`
    }
    if err := json.Unmarshal(body, &p); err != nil {
        return nil, err
    }
    subject := ""
    if task, ok := p.Data["task"].(map[string]any); ok {
        if title, ok := task["title"].(string); ok {
            subject = title
        }
    }
    sum := sha256.Sum256(body)
    return &model.Event{
        ID:      fmt.Sprintf("vikunja:%s:%x", p.EventName, sum[:8]),
        // Source 由 handler 按配置实例名填入
        Type:    p.EventName,
        Time:    p.Time,
        Subject: subject,
        Data:    p.Data,
        Raw:     body,
    }, nil
}
```

> Vikunja 的 `event_name` 含 `task.created`、`task.updated`、`task.reminder.fired` 等；配置中用 `type: "task.reminder.*"` 收窄，避免噪音。
