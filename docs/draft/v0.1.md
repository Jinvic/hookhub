# HookHub 设计文档（草案 v0.1）

> **一句话定位**：HookHub 是一个可插件化扩展的 Webhook 中间件——从任意服务接收 Webhook，按规则解析、转换并转发到任意目标。
>
> *Receive webhooks from anywhere, route them anywhere.*

---

## 1. 背景与目标

### 1.1 问题

各类 SaaS / 自建服务（Vikunja、GitHub、Gitea、Uptime Kuma…）都支持 Webhook 推送，但：

- 推送内容是**原始 JSON**，直接接入 IM/通知服务（ntfy、Slack、邮件）可读性差；
- 每个服务的 payload 结构不同，逐个硬编码对接成本高、难维护；
- 一个事件往往要**扇出**到多个目标（手机推送 + 群通知 + 存档）。

### 1.2 目标

- **多来源接入**：一个统一入口 `/hook/{source}` 接收不同服务的 Webhook。
- **统一事件模型**：各来源解析为统一的 `Event`，下游与来源解耦。
- **配置化路由**：用 YAML 定义「匹配规则 → 模板渲染 → 投递目标」，常见需求零代码。
- **可插件扩展**：新增来源/目标 = 新增一个文件 + 注册，不改核心流程。
- **可靠投递**：异步处理、失败重试、幂等去重、可观测。

### 1.3 非目标（v0.1 不做）

- 可视化 Web UI / 规则编辑器（后续版本）。
- 多租户 / 权限体系。
- 分布式部署与集群调度（单实例起步，接口预留）。

## 2. 总体架构

```
                  ┌─────────────────┐
 Vikunja ─POST──▶ │ /hook/vikunja   │─┐
 GitHub  ─POST──▶ │ /hook/github    │─┤   ┌────────┐   ┌──────────┐   ┌────────┐
 Gitea   ─POST──▶ │ /hook/gitea     │─┼──▶│ Router │──▶│ Pipeline │──▶│  Sink  │──▶ ntfy / Slack / ...
 ...     ─POST──▶ │ /hook/{source}  │─┘   │(rules) │   │(render)  │   │(send)  │
                  └─────────────────┘     └────────┘   └──────────┘   └────────┘
                        │                      ▲
                   Source 插件            配置驱动 (config.yaml)
                 (验签 + 解析 → Event)
```

**数据流**：

1. HTTP 入口按 `{source}` 找到对应 Source 插件；
2. Source 验签并解析为统一 `Event`；
3. Router 用配置规则匹配 Event，产出若干 Action；
4. Pipeline 对每个 Action 渲染模板，生成 `Message`；
5. Sink 将 `Message` 投递到目标，失败进入重试队列。

**设计原则**：

- **三层解耦**：Source（来源）→ Event（统一模型）→ Sink（目标），核心流程对具体服务无感知。
- **配置优先**：能用 YAML 表达的绝不写代码；模板不够用时再降级到脚本（后续）。
- **编译期插件**：v0.1 采用注册表 + `init()` 自注册，单二进制分发，简单可靠。

## 3. 核心数据模型

### 3.1 Event（统一事件）

```go
type Event struct {
    ID      string          // 幂等键：source + type + payload hash
    Source  string          // "vikunja"
    Type    string          // "task.reminder.fired"
    Time    time.Time       // 事件发生时间（优先取 payload，否则接收时间）
    Subject string          // 可选摘要，如 task.title
    Data    map[string]any  // 解析后的结构化数据
    Raw     []byte          // 原始 body，供模板兜底与调试
    Headers http.Header
}
```

### 3.2 Message（待投递消息）

```go
type Message struct {
    Title    string
    Body     string
    Priority string            // 供 ntfy 等使用，可选
    Tags     []string
    Format   string            // "text" | "markdown"
    Extra    map[string]string
}
```

### 3.3 Action / Route（配置模型）

```go
type Route struct {
    Name    string
    Match   Match
    Actions []Action
}

type Match struct {
    Source string // 精确或通配 "vikunja"
    Type   string // 通配 "task.reminder.*"
    When   string // CEL 表达式，如 `data.task.project_id == 4`
}

type Action struct {
    Sink     string
    Config   map[string]any
    Template Template
}

type Template struct {
    Title    string
    Body     string
    Priority string
    Tags     []string
    Format   string
}
```

## 4. 插件接口

### 4.1 Source 接口

```go
type Source interface {
    Name() string
    Verify(req *http.Request, body []byte, cfg SourceConfig) error
    Parse(req *http.Request, body []byte) (*Event, error)
}
```

- `Verify`：验签 / 共享密钥校验，允许空实现（v0.1 提供 `none` 与 `hmac` 两种通用策略，插件可复用）。
- `Parse`：将原始请求转为 `Event`。

### 4.2 Sink 接口

```go
type Sink interface {
    Name() string
    Send(ctx context.Context, msg *Message, cfg map[string]any) error
}
```

### 4.3 注册表

```go
var sources = map[string]Source{}
var sinks   = map[string]Sink{}

func RegisterSource(s Source) { sources[s.Name()] = s }
func RegisterSink(s Sink)     { sinks[s.Name()] = s }

// 各插件在 init() 中自注册
func init() { RegisterSource(&VikunjaSource{}) }
```

新增一个服务支持 = 新增一个文件 + `init()` 注册，主流程零改动。

## 5. 配置设计

### 5.1 示例（Vikunja → ntfy）

```yaml
server:
  addr: ":8080"
  log_level: info

sources:
  vikunja:
    type: vikunja
    secret: "${VIKUNJA_WEBHOOK_SECRET}"

sinks:
  ntfy-work:
    type: ntfy
    base_url: https://ntfy.sh
    token: "${NTFY_TOKEN}"

routes:
  - name: vikunja-reminder-to-ntfy
    match:
      source: vikunja
      type: "task.reminder.*"
      when: 'data.task.project_id == 4'
    actions:
      - sink: ntfy-work
        config:
          topic: work-tasks
          priority: high
          tags: ["bell"]
        template:
          title: "⏰ {{ .Data.task.title }}"
          body: |
            项目：{{ .Data.project.title }}
            提醒时间：{{ .Data.reminder.reminder }}
            链接：https://vikunja.example.com/projects/{{ .Data.project.id }}
          format: markdown
```

### 5.2 配置要点

- **环境变量插值**：`${VAR}` 在加载时替换，避免密钥落盘。
- **模板引擎**：Go `text/template`，数据上下文为 `Event`（`{{ .Data.xxx }}`、`{{ .Subject }}`、`{{ .Type }}`）。
- **条件表达式**：CEL（`cel-go`）实现 `when`，兼顾安全与表达力。
- **通配匹配**：`Type` 支持 `*` 前缀/后缀，如 `task.*`、`task.reminder.*`。
- **扇出**：一个 Route 的多个 Action、多个 Route 匹配同一 Event，均会依次执行。

## 6. 处理流水线

```
HTTP Handler
  ├─ 1. 路由到 Source（按 path {source}）
  ├─ 2. 读取 body（限流，默认 1MB）
  ├─ 3. Verify（失败 401）
  ├─ 4. Parse → Event（失败 400）
  ├─ 5. 幂等检查（ID 去重，命中则 200 并跳过）
  ├─ 6. 立即返回 200（避免上游超时重投）
  └─ 7. 投递到内部队列 → 异步处理
        ├─ Router.Match(event) → []Action
        ├─ 对每个 Action：渲染模板 → Message
        └─ Sink.Send（超时 + 重试 + 日志）
```

**关键决策**：

- **先 ACK 后处理**：handler 快速返回 2xx，处理异步化，避免上游重试风暴。
- **重试策略**：指数退避（如 1s/5s/30s/2m，最多 4 次），超过阈值记失败日志并丢弃（v0.1 不做死信队列，接口预留）。
- **去重**：内存 LRU（默认 1 万条）即可满足单实例；接口预留 Redis 实现。

## 8. 关键接口与模块职责

| 模块 | 职责 | 关键点 |
| --- | --- | --- |
| `config` | 解析 YAML、插值 env、校验 | 启动即校验，失败快速退出 |

| `pipeline` | 编排全流程 | 异步、扇出、错误隔离 |
| `sink` | 投递到目标 | context 超时、错误分类 |
| `dedup` | 幂等 | LRU，接口预留 |
| `queue` | 异步 + 重试 | 有界队列，背压策略 |

## 9. 可靠性与可观测性

### 9.1 可靠性

- **验签**：每个 Source 强制实现 `Verify`，默认 `none` 需显式配置。
- **幂等**：`Event.ID` 去重，防重投。
- **超时**：Sink 调用默认 10s context 超时。
- **重试**：指数退避，错误分级（可重试 5xx/超时，不可重试 4xx）。
- **背压**：队列有界，满时丢弃并告警（v0.1），后续可改阻塞/落盘。

### 9.2 可观测性

- **结构化日志**（`slog` JSON）：记录 `event_id / source / type / route / sink / duration / result`。
- **调试模式**：`/hook/{source}?debug=1` 只记录原始 payload，不转发，便于新接入服务时探查结构。
- **健康检查**：`/healthz`、`/readyz`。
- **指标（可选）**：Prometheus `/metrics`，暴露接收数、转发数、失败数、延迟。

## 10. 安全设计

- Webhook 验签（HMAC / Token），密钥通过环境变量注入。
- Body 大小限制（默认 1MB），防止内存攻击。
- 模板渲染禁止执行任意代码（`text/template` 天然安全）；CEL 沙箱求值。
- 目标地址白名单（可选配置），防止被用作 SSRF 跳板。
- 日志中敏感字段脱敏（token、secret）。

## 14. 附录：Vikunja Source 解析示例

```go
func (v *VikunjaSource) Parse(_ *http.Request, body []byte) (*Event, error) {
    var p struct {
        EventName string         `json:"event_name"`
        Time      time.Time      `json:"time"`
        Data      map[string]any `json:"data"`
    }
    if err := json.Unmarshal(body, &p); err != nil {
        return nil, err
    }
    sum := sha256.Sum256(body)
    return &Event{
        ID:      fmt.Sprintf("vikunja:%s:%x", p.EventName, sum[:8]),
        Source:  "vikunja",
        Type:    p.EventName,
        Time:    p.Time,
        Subject: gjson.GetBytes(body, "data.task.title").String(),
        Data:    p.Data,
        Raw:     body,
    }, nil
}
```

> Vikunja 的 `event_name` 含 `task.created`、`task.updated`、`task.reminder.fired` 等，推荐配置中用 `type: "task.reminder.*"` 精确收窄，避免噪音。
